# B4 定稿：验收后的“保存 / 放弃 / 撤销”（依据草稿 + ChatGPT 评审 R01–R11）

规划会话，2026-11-08。取代 B4-plan-draft.md。评审 11 项全部采纳（R09 部分采纳，见第 7 节）。

## 1. 受控 Git 执行层（R01、R11）
- 宿主所有 git 调用（含 add、status、diff、commit、merge、read-tree、worktree、branch）只经一个函数，固定附加：
  `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c commit.gpgsign=false -c tag.gpgsign=false -c diff.external= -c core.pager=cat`，diff 加 `--no-ext-diff --no-textconv`，提交与合并加 `--no-verify`；环境变量 `GIT_TERMINAL_PROMPT=0`、`GIT_EXTERNAL_DIFF` 清空、`GIT_CONFIG_NOSYSTEM=1` 不设（会改变用户语义，不做）。
- **外部驱动检测**：保存前读取副本与主项目的 `.gitattributes`（含子目录）和 `git check-attr`，若任一路径使用 `filter=`、`merge=`（非内置 text/binary/union）或 `diff=` 且该驱动在生效配置里定义了外部程序 → **停止自动保存**，报告“这个项目使用了需要外部程序处理的文件类型，工作台暂不支持自动保存”，副本保留。不得关闭驱动后继续（会改变文件内容语义）。git-lfs 同样归入此类（首版不支持）。
- 哨兵实测：合成恶意 hooksPath 钩子、filter/merge/diff 驱动、fsmonitor 钩子、gpg.program，各指向一个写哨兵文件的脚本；跑完保存/放弃/撤销/读证据全流程，哨兵文件一个都不得出现（filter/merge 场景应在检测处停下）。
- 验收卡如实写：“为保证安全，保存时没有运行项目自定义的提交检查。”（仅当项目确有 hooksPath 或 .git/hooks 下有可执行钩子时显示。）

## 2. 验收内容冻结（R03）
- 生成验收证据时，用 `git add -A` 到一个**临时索引**（GIT_INDEX_FILE 指向 .studio 内），`git write-tree` 得到 tree id，记为 `acceptedTree`，验收卡与检查结果都绑定它。检查脚本在该内容上运行（运行前后各算一次 tree，运行中被改动则检查无效）。
- 保存时再算一次 tree：不等于 acceptedTree → 原验收失效，状态回到需重新检查，禁止保存。提交时用 `commit-tree acceptedTree`（父=任务基线）生成任务提交，保证提交内容就是验收内容。
- 测试运行产生的文件会进入 tree：检查后算出的 tree 若与检查前不同，记为“检查改动了文件”，检查结果作废并提示（首版不自动清理）。

## 3. 保存（R02、R05、R07、R08）
- 前提（核心层判定，界面不能绕过）：检查无失败项、执行体正常结束、无隔离异常、用户已逐条确认验收标准；验收标准为空时，用户须确认“我已看过改动，结果符合我的要求”。**未检查**可保存（显示“没有自动检查”）；**检查失败/执行异常**不可保存，只能放弃或保留副本以后处理。不新增“仍然保存”。
- 绑定开工时的仓库路径、分支名、基线 HEAD。保存前：分支变了 → 停止，提示“项目当前所在的版本线和开工时不同，工作台不会自动保存”，不让用户选分支。
- 主项目有未提交改动（忽略 .studio/）→ 停止，提示“项目中还有其他未保存的修改，请先处理后再保存”，列出文件名，副本保留。不提供“帮你保存”。
- 合并：主项目 HEAD 等于基线 → 快进到任务提交之上的 --no-ff 合并提交；不等于 → 尝试 --no-ff 合并；冲突 → abort，然后**核验**主项目 HEAD 与工作区与合并前一致，提示“AI 的修改与项目当前版本有冲突，工作台无法安全自动合并。本次没有保存，AI 的成果仍保留。”选项：放弃 / 在当前版本上重新执行（新任务，沿用计划）。核验不一致 → 报“项目状态异常，请不要继续操作”并保留全部现场。

## 4. 放弃（R10）
- 删除副本与任务分支。提示“这次任务的代码改动不会进入项目。”扩展了额外目录或用了完全信任的任务追加：“AI 在任务副本以外做过的修改（如额外文件夹、联网操作）工作台无法撤销。”

## 5. 撤销这次保存（R04）
- 仅当：该任务的合并提交是当前分支 HEAD、分支与保存时一致、工作区干净 → 以新提交恢复到合并前的提交（`restoreTo(合并前 HEAD)`，此时等价于只撤这一次）。
- 否则不提供撤销，说明“这次保存之后项目还有其他修改，暂时不能只撤销这一项”。“整体回到某个旧版本”不在 B4。
- 撤销同样受第 1 节外部驱动检测约束。

## 6. 操作日志与中断恢复（R06）
- 保存/放弃/撤销各写阶段日志到任务记录：开始、合并前 HEAD、任务提交、合并提交、清理各步结果；每步完成后立即落盘。
- 状态细分：`saved`、`saved_cleanup_pending`、`save_failed_unmerged`、`discarded`、`discard_cleanup_pending`、`undone`、`undo_failed`。清理（worktree remove、分支删除）失败不吞错，记为 cleanup_pending，界面显示“已保存，临时文件还没清理干净”，提供“重试清理”。
- 应用启动时对未完成的操作按 Git 真实状态核对（合并提交是否在分支上、worktree 是否还在）并修正记录；无法判定 → 标“需要人工查看”，不自动动手。
- 按钮操作幂等：同一操作进行中再次点击被拒绝。清理只删除 .studio/worktrees/<本任务 id> 与 studio/task-<id> 分支，不删其他东西，不结束任何进程。

## 7. 验收界面（R09，部分采纳）
- B4-2 补：改动的文件清单 + 每个文件的差异查看（只读，大白话标注“新增/修改/删除”）；验收标准逐条勾选；空标准时的整体确认；“尚未提供网页预览，请在保存后自己打开看看，不满意可以撤销”的提示。
- 不做：网页预览（另行排期，需在沙箱或完全信任下运行，见 B3-1 1.4）、AI 生成的改动摘要。
- 维护者优先“先跑通”，因此 B4 完成标准为：保存/放弃/撤销闭环可用 + 上述最小证据；不宣称“完整的用户级验收闭环”。
