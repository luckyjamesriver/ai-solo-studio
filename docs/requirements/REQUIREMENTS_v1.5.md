# AI Solo Studio — 需求规格 v1.5

- **文档版本**: v1.5.0
- **状态**: 已批准（2026-11-07）
- **日期**: 2026-11-07
- **基于**: v1.4；吸收 ChatGPT 评审（结论：有条件通过，路线图需调整）。本文只写新增与变更，未提及章节沿用 v1.4。
- **背景**: docs/PROJECT_CONTEXT.md

---

## 1. 本版的核心新增（一句话）

**让 AI 帮助用户形成更可靠的开发决定，并把决定无损交给执行层；而不是让 AI 之间进行更多讨论。**

产品中心不变：让普通创作者成功管理软件项目。多 AI 协作是内部能力，不是产品中心。

## 2. 变更摘要

| 变更 | 原因 |
|---|---|
| 新增**最小思考层**：起草 → 一次独立评审 → 整理分歧 → 用户批准 → 生成任务 | 减少人工搬运；双模型互审在本项目中改变过方向 |
| 评审意见**结构化**，评审者职责为“找错”而非“求共识” | 轮数上限防不了错误共识 |
| 额度接手改为**步骤级**，且只作为可靠性增强 | 防止接手者改变已批准方向、把自审当互审 |
| **删除**订阅类集成的“高级选项”；新增**外部执行交接**（任务导出、报告导入） | 用户勾选不能替代合规授权；交接方式让任何官方工具都能接活 |
| 凭证规则细化 | 区分“提取他人凭证”（禁止）与“本应用按官方流程获取的令牌”（允许并保护） |
| 能力按**四类**控制：文件读写、命令执行、外部网络、凭证访问 | 运行项目脚本本身不是低风险；worktree 隔离不等于权限隔离 |
| 隔离改为**启动前构建、启动后核验** | 事后发现已启动的服务为时已晚 |
| **双轨验证**：维护者自用 + 入门用户尽早试用 | 防止产品演变为个人 AI 控制台 |
| 产物**分层存放** | 防止“项目即记忆”变成“项目即日志仓库” |
| 交接协议加强：锁的所有权与过期处理；报告绑定 Git 状态 | 文件存在不等于任务正在执行 |

## 3. 最小思考层

### 3.1 流程（M3-A 唯一范围）
```
用户提出问题
  → 规划者起草方案
  → 评审者独立评审一次
  → 规划者逐条处理评审意见，整理出“已解决 / 未解决 / 交用户裁决”
  → 【用户批准方案】
  → 生成任务（带编号，遵守交接协议）
执行报告返回后 → 规划者审查一次 → 【用户决定下一步】（系统不自动开始下一个任务）
```
- 默认一轮评审、一次修订。仅当出现**新的重大事实**才允许第二轮。
- 每次调用都是基于项目资料的独立调用，不维护长期 AI 会话。

### 3.2 角色与权限
- 规划者（默认 Claude）、评审者（默认 ChatGPT），用户可关闭评审者（单思考者模式）。
- **评审者的职责是发现规划者可能犯的错误，不是帮助达成共识。**
- 思考者只返回结构化内容，**不获得任何工具或文件系统权限**；由宿主程序受控保存产物。

### 3.3 评审意见格式（每条必填）
| 字段 | 说明 |
|---|---|
| 问题 | 具体反对或质疑什么 |
| 严重程度 | 阻断 / 建议 / 信息补充 |
| 依据 | 来自哪份需求、代码或事实；缺乏依据须注明 |
| 影响 | 不修改会造成什么结果 |
| 建议 | 最小修改方式 |
| 处理结果 | 已解决 / 未解决 / 交用户裁决（由规划者填写并说明理由） |

- 存在未解决的阻断意见 → 必须交用户裁决，不得派工。
- 双方一致但缺乏依据的结论 → 标注“未经证实”，不得视为已验证。
- 评审者需要更多资料时，应列出需要哪些证据，不得自行补全事实。

### 3.4 停止条件
任一满足即停止并交用户：轮数达到上限；费用或额度达到预算；耗时超限；方案范围较原始需求发生实质变化；存在未解决的阻断问题。

### 3.5 上下文（分层，“项目即记忆”）
- 第一层（每次必带）：项目目标与不变约束（PROJECT_CONTEXT 的核心部分）。
- 第二层（按需）：当前任务、相关 ADR 与需求章节、相关证据。
- 第三层（必要时引用）：历史讨论。
- 评审者获得：原始需求、约束、验收标准、相关决定、规划者方案；不获得规划者的完整思考过程。
- 每次调用记录：发送了哪些资料、发给哪家服务。界面可查看。资料发送给外部 AI 服务即视为数据离开本机，首次使用须告知用户。

### 3.6 步骤级接手（M4 起，按需）
| 情形 | 处理 |
|---|---|
| 确认额度用尽 | 询问用户是否由另一模型接手 |
| 短暂限流 | 按服务给出的等待时间重试，不立即切换 |
| 请求超时 | 先确认原请求是否已完成，防止重复生成 |
| 上下文超限 | 按分层规则压缩，保留约束与证据 |
| API Key 失效或余额不足 | 停止该服务，提示用户处理 |
| 只返回了部分内容 | 标为不完整，不得作为正式产物 |
| 两个服务都不可用 | 暂停，保留全部已完成产物 |
| 评审者接手规划 | 明确标注“本轮失去独立评审”，不得视为互审 |

- 每个已完成步骤的产物有版本；接手者只执行未完成步骤，不得改变已批准的方向。

### 3.7 成本
- Claude（API Key）：调用前估算、任务预算、硬上限（到达即停止，模型不得自行追加），完成后显示实际消耗。
- ChatGPT（计划）：显示额度与使用状态，不虚构按 Token 计算的金额。
- 两者分开记录；普通用户默认只看预计区间与实际消耗，预算设置放在高级设置。

## 4. 执行方式与接入

| 方式 | 级别 |
|---|---|
| Codex app-server（ChatGPT 计划） | 正式支持；对外测试前按官方 Sign in with ChatGPT 流程完成授权，不以本机现有 Codex 登录作为对外方案 |
| Claude（API Key） | 正式支持 |
| DeepSeek（API Key） | 可作为模型提供方；执行能力须经验证（M5） |
| **外部执行交接** | 正式支持：导出符合交接协议的任务文件，用户在任意官方工具（如 Claude Code、Antigravity）中自行运行，再导入报告；本应用不接管这些工具的身份 |
| Claude Code 订阅集成、Antigravity 集成 | 不提供，除非获得官方明确授权 |
| 嵌入或程序化驱动消费级网页 | 不支持 |

**凭证规则**：禁止提取、复制、复用其他工具的登录凭证；允许按官方授权流程取得本应用自己的 OAuth 令牌，并加密保存、按官方方式刷新。

## 5. 能力授权与隔离

### 5.1 四类能力分别控制
| 类别 | 默认 |
|---|---|
| 文件读写 | 仅任务 worktree |
| 命令执行 | 每次询问（运行项目脚本属于命令执行，可启动任意子进程） |
| 外部网络 | 关闭 |
| 凭证访问 | 不提供 |

用户配置的 MCP、连接器、插件、自定义指令默认全部关闭；计划卡可逐个授予，每项注明属于哪类能力及风险。

### 5.2 启动前构建、启动后核验
- 启动执行体之前构建经过验证的最小权限环境；获取配置信息的过程本身不得启动用户的 MCP 等扩展。
- 启动后再次核验实际启用的能力。
- **任一关键保护无法确认，不得声称隔离成功**，任务不得开始。
- 无法关闭的部分（如全局 AGENTS.md）在环境体检中如实提示。

## 6. 验收：证据先行
（同 v1.5 草案第 6 节）询问“验收标准是否达成”之前，先展示改动对比、预览入口、自动检查结果；用户未查看任何证据就确认时给出一次轻提示；验收卡记录用户查看过的证据。

## 7. 交接协议（加强）
- 锁按项目、任务、工作树定义所有权，记录会话名称、进程标识、开始时间、当前状态；发现锁时先核实持有者是否仍在运行，再决定恢复或释放，过期锁不得被静默覆盖。
- 报告绑定：任务编号、开始与结束时的 Git HEAD、工作树、测试证据、产物版本。
- 外部执行交接与内部执行使用同一协议。

## 8. 产物存放
| 内容 | 位置 | 入库 |
|---|---|---|
| 临时对话、流式事件、错误、详细日志 | .studio/threads/ | 否 |
| 已批准的方案与任务范围 | docs/plans/ | 是 |

## 10. 验证假设（替换 H5～H7）

**思考层对照实验**：同一组真实开发任务，比较三种流程：
- A：单模型规划后直接执行；
- B：双模型，人工交接评审；
- C：双模型，自动交接评审。

衡量：提前发现的实质性缺陷、实际人工操作时间、返工次数、增加的费用与等待。
- C 仅比 B 少搬运、质量无差异 → 只保留自动交接能力，不建设更复杂的多模型编排；
- B、C 都明显优于 A → 考虑把“第二意见”升级为默认能力。

## 11. 明确不做（v1.0 前）
多执行体自动分工；思考层直接修改代码或绕过人工检查点；系统自动开始下一个任务；订阅凭证类第三方集成；内嵌或程序化驱动官方网页；MCP 隧道与移动端审批；非网页类项目；完整的多 Agent 编排与统一配置中心（推迟）。
