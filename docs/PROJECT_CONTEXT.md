> 给任何参与本项目的 AI（规划者、评审者、执行体）以及新加入的人：开始工作前先读这份文档。
> 它记录“为什么是现在这样”。具体规格见 docs/REQUIREMENTS_REPORT.md（索引：v1.4 + v1.5），具体决定见 docs/adr/。

## 1. 一句话

面向独立创作者的 AI 软件开发与验收工作台：**你决定做什么，AI 负责实现，工作台负责证明结果、控制风险、随时可撤销。**

## 2. 核心信念（不要偏离）

- **AI 越来越会“实现”，但“这个东西对谁有用、用起来对不对”的判断属于人。** 人最懂人性。产品把人的判断放在最关键的位置，把 AI 的执行力放在最费力的位置。
- **AI 自述不是证据。** 任务状态只来自真实信号：进程退出码与结果事件、构建与测试结果、用户确认。
- **不假装。** 不确定就显示“未检查”；做不到的能力不伪装（例如不支持暂停就只提供“停止”）。
- **默认安全，有边界的恢复。** 隔离施工；高风险操作由人批准；能撤销什么、不能撤销什么，执行前说清楚。

## 3. 项目是怎么走到今天的

| 阶段 | 发生了什么 | 留下的教训 |
|---|---|---|
| v1.2（演示版） | 设想“双 PM（Claude + ChatGPT）研讨 + 多执行体分工 + 内嵌官方网页 + MCP 隧道”，面向零基础用户。由 AI 快速搭出演示代码。 | 功能多但不可信：伪造成功状态、默认跳过权限、Electron 安全配置不当、写死个人路径、后端放在 Vite 开发服务器里。 |
| v1.3 | 收窄为“入门级创作者”的单一闭环。 | 零基础用户过不了安装关；专业用户已有官方工具。中间人群才是空白。 |
| 外部评审 | ChatGPT 评审指出：核心不该是“更易用的编码界面”，而是**验收与恢复**；建议优先网页项目、按需澄清、有边界的恢复。 | 双模型互审确实产生了改变方向的价值（这是“思考层”的实证来源）。 |
| v1.4（重建基线） | 推倒演示代码，在 rebuild 分支从零重建。 | 先打基础：安全外壳、核心引擎、测试，再接真实 AI。 |
| M0/M1 完成 | 安全的 Electron 外壳 + 纯 Node 核心引擎，44 项测试，CI。 | 见第 7 节“踩过的坑”。 |
| v1.5 | 吸收 ChatGPT 评审：缩小思考层、删除订阅类高级选项。 | 用户勾选不能替代合规授权；多 AI 协作是内部能力，不是产品中心。 |
| M2 完成 | 选定 Codex app-server 为第一个执行体；适配器、配置隔离、试用脚本；收尾轮修复停止竞态、加入被拒操作记录、补全配置隔离、声明已验证版本（0.166.0）。 | 技术上能接通 ≠ 条款允许。**停止竞态**：准备阶段收到的停止请求曾被静默丢弃，任何“请求被吞掉的窗口”都必须消除，并用确定性测试覆盖。**拒绝记录**：用户拒绝的操作不能只留一句文字，要结构化进入验收卡，否则“退出码 0 + 有改动”会掩盖任务不完整。**配置隔离不完整**：能关的（MCP、连接器、插件、自定义指令）已关；AGENTS.md 无官方关闭方式，已作为已知限制记录（ADR 0001）。 |

## 4. 目标用户

**主画像**：已经借助 AI 做出过一点东西（小网站、小工具），想继续加功能、修问题，却难以掌控的人。会装软件、懂项目文件夹，但看不懂 diff、不会处理 Git、看到报错会慌。
**第一位用户是维护者本人**：先“用自己的产品开发自己的产品”，把流程磨顺，再为入门用户简化。
**MVP 范围**：本地网页类项目。目标用户包括中国大陆的创作者，网络可达性与成本是真实约束。

## 4.1 竞争与参考

- **GitHub Agent HQ**：中立平台的多 Agent 协作，面向专业开发者；我们面向的是更靠近创作者的中间人群，差异在验收与恢复。
- **Agents Anywhere**（https://github.com/anywhere-labs/Agents-Anywhere ，MIT）：跨设备远程控制 Codex / Claude Code / DeepSeek Harness，审批与中断已具备，未见 worktree 隔离与验收卡；其 Runtime 协议与 Connector 是我们适配器设计的重要参考，后端主要为 Python。
- **更正**：此前所说的“Harness”指 **DeepSeek Harness（DSH）**，疑似社区项目，待核实许可与调用方式。

## 5. 当前架构（简）

- `src/core/`（纯 Node，可独立测试）：proc（子进程，不经 shell、真实退出码、停止升级信号）、task（状态机、编排器、持久化）、git（worktree 隔离、保存、撤销、冲突、回到保存点）、executor（统一接口 + 适配器）、policy（风险分级）、checks（build/test）、acceptance（验收卡）、env（环境体检）。
- `src/main` + `src/preload` + `src/renderer`：Electron，contextIsolation/sandbox 开启，渲染进程只能用白名单 API。
- 关键状态规则：`exec_succeeded` 只表示执行体正常结束，**不代表任务完成**；保存必须经过验收卡并由用户确认验收标准。
- 详见 docs/ARCHITECTURE.md。

## 6. 关键决定与理由

| 决定 | 理由 | 出处 |
|---|---|---|
| 只做一个闭环：需求 → 计划 → 批准 → 隔离施工 → 验收 → 保存/撤销 | 功能多不如一件事做可靠 | 需求 v1.4 |
| 每个任务在独立 Git worktree 中执行 | 主线在用户点“保存”前不受影响；中断不回滚的副作用由撤销兜底 | 架构 |
| 第一个执行体：Codex（app-server） | 有官方审批接口与 schema；OpenAI 官方支持开源本地应用使用用户的 ChatGPT 计划（Sign in with ChatGPT） | ADR 0001 |
| Claude Code 仅以 API Key 模式作为第二个执行体 | Anthropic 不允许第三方产品代用户使用订阅凭证；权限回调格式缺少完整官方文档 | ADR 0001 |
| 第一版不接入 Antigravity；将来优先 Gemini API key，agy 登录仅作用户主动开启、先披露封号风险的高级选项 | 条款表述与社区答复矛盾，且后果可能波及整个 Google 账户 | ADR 0001、ADR 0009 |
| 删除“高级选项”；不做订阅类集成（Claude Code 订阅、Antigravity） | 用户勾选不能替代服务方的合规授权 | ADR 0002、需求 v1.5 |
| 外部执行交接：导出任务、用户在官方工具中运行、导入报告 | 任何官方工具都能接活，本应用不接管其身份 | ADR 0002、需求 v1.5 §4 |
| 四类能力分别控制：文件读写、命令执行、外部网络、凭证访问（MCP/连接器/插件/自定义指令默认关闭，逐个授予） | worktree 隔离不等于权限隔离；运行项目脚本本身就是命令执行 | 需求 v1.5 §5 |
| 隔离“启动前构建、启动后核验”；任一关键保护无法确认就不开始任务 | 事后发现已启动的服务为时已晚；获取配置的过程本身也不得启动扩展 | 需求 v1.5 §5.2 |
| 产物分层存放：临时日志 .studio/threads/（不入库）；方案 docs/plans/、决策 docs/adr/、验收摘要 docs/changelog/（入库）；凭证放系统受保护存储 | 防止“项目即记忆”变成“项目即日志仓库” | 需求 v1.5 §8 |
| 依赖与运行时固定精确版本，升级选发布满两周的最新补丁版本 | 防止版本悄悄变化与供应链风险 | docs/checklists/M1.md |
| 不复制许可证不兼容的代码（如 OpenAI SIWC DevKit 为非商业许可） | 本项目为 MIT | ADR 0001 |

## 7. 踩过的坑（不要再踩）

- **Node 26 下 Electron 安装会静默失败**（解压中途退出、install 返回 0）。开发固定 Node 22（.nvmrc）。
- **用户全局配置会泄漏进执行**：用户的 AI 工具全局配置可能关闭沙箱或自动允许操作，用户的 MCP 服务器与连接器也会进入会话。适配器必须显式传入全部安全参数、隔离用户全局配置，并有测试保证；做不到的（如 AGENTS.md）要如实记为已知限制。
- **停止请求不能有被吞掉的窗口**：start() 的准备阶段、执行体刚启动时 stop() 都必须生效。
- **对用户配置里不存在的 MCP 名字写 enabled=false 会让 Codex 无法启动**：名单必须来自 `config/read`，不能用 `codex mcp list`。
- **退出码 0 不代表成功**：权限被拒或任务失败时执行体可能仍返回 0。必须解析结果事件。
- **Codex 的工作区写入模式默认允许写系统临时目录**：worktree 外一律按高风险、不可恢复处理。
- **中断不回滚已落盘的那一步。**
- **`npm audit fix --force` 会悄悄跨大版本升级**：禁止使用。
- **依赖固定毫秒数的测试会偶发失败**：测试应等待条件成立，而非延长等待时间。
- **DevTools Console 默认拦截粘贴**：安全检查改用 `npm run smoke` 自动完成。

## 8. 工作方式（当前）

角色：
- **规划者（Claude）**：起草方案、审查报告、维护本文档与需求文档。
- **评审者（ChatGPT）**：对方案提出挑战与补充。
- **执行体（Claude Code 等）**：在本机按任务文件实施，写报告。
- **维护者（人）**：决定方向、追加需求、在关键节点拍板，亲自做 AI 做不了的验收（例如看窗口）。

交接协议（文件即接口）：
- 任务：`next-task.md`（目标、约束、验证要求、报告要求）。
- 报告：`report.md`（做了什么、证据、问题、提交哈希）。
- 决定：`docs/adr/`；规格：`docs/REQUIREMENTS_REPORT.md`；本文档记录背景与理由。

执行体的通用约束：
- 每项改动单独提交；推送 rebuild 分支须有任务文件中的明确指示（规划会话在审查通过后下达，维护者已授权）；未经指示不推送；合并到 main 须维护者确认。
- 禁止任何跳过权限或关闭沙箱的参数；安全断言（tests/security.test.ts 等）只能变严、不能放宽，任何修改须在报告中逐条标明原断言与新断言。
- 不改用户全局配置；不写死个人路径。
- 每一步都要验证：typecheck、test、build、smoke；报告写清证据与不确定之处。

人工节点（必须由维护者决定）：方案定稿（里程碑级）、合并到 main 与发布、跨大版本升级、涉及条款风险的接入、外发资料或消耗外部服务额度、放宽安全断言或安全设置、接触凭证。
审查通过后的 rebuild 分支推送与开发类技术决定由规划会话下达（维护者 2026-11-08 授权）。

## 9. 与维护者协作的偏好

- 使用中文；说明用大白话，少用术语，必要时解释。
- 诚实优先：做不到、没验证、不确定，都要直说。
- 给结论和建议，并说明理由；重要决定交给维护者拍板，不替他做。
- 一次只问一个关键问题。
