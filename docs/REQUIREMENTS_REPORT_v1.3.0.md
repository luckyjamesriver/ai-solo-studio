## 1. 背景与判断

### 1.1 一个被忽略的中间人群
当前 AI 编码工具大致分成两端：

- **专业端**：Claude Code、Codex、Cursor、Antigravity 及大量开源多 Agent 编排 GUI。功能强，但默认用户懂终端、Git、构建系统和 diff。我们实际试用同类开源编排 GUI 后的结论是：**它们几乎都面向专业开发者，入门者使用非常吃力。**
- **全托管端**：面向零基础用户的“一句话生成应用”云平台。门槛低，但项目在平台里、可控性和可迁移性有限，做到一定复杂度后容易卡住。

两端之间存在一个正在快速扩大的人群：**懂一点入门知识、想亲手做自己的东西、但不想也来不及成为专业工程师的人**——独立创作者、设计师、业务创始人、学生、业余开发者。这个人群目前没有一个“为他们设计”的本地 AI 编码工作台。

### 1.2 为什么是“人 + AI”，而不是“AI 全包”
AI 在“实现”上的能力正在快速逼近甚至超过人，但在相当长的一段时间内存在一个**“时差”**：

- AI 擅长把清晰的需求变成代码；
- 人擅长判断**这个东西对谁有用、用起来感觉对不对、哪些细节会让人在意**——也就是对“人性”的理解。

本产品的设计哲学由此而来：**不追求让 AI 替人做所有决定，而是把人的判断力放在最关键的位置，把 AI 的执行力放在最费力的位置。**

## 2. 目标用户画像

### 2.1 主画像：入门级创作者
- 能独立安装桌面软件、登录账号、按提示完成简单配置；
- 用过网页版 ChatGPT / Claude，可能用过 Cursor，但主要是“聊天 + 复制粘贴”；
- 知道“项目文件夹”“代码文件”是什么，**但看不懂 diff、不会处理 Git 冲突、看到报错会慌**；
- 已经有或愿意购买 1～2 个 AI 订阅；
- 想做的东西：个人工具、小网站、作品集、内部小系统、副业产品的 MVP。

### 2.2 非目标用户（v1.x 不刻意服务）
- **完全零基础、不愿接触任何本地安装的用户**：更适合全托管云平台；
- **资深工程师**：官方 CLI 与专业编排工具对他们更高效。

### 2.3 用户最核心的三种恐惧（产品设计的出发点）
1. **“我不知道它改了什么。”** → 每次改动都要有大白话说明；
2. **“它会不会把我的东西搞坏？”** → 隔离执行 + 一键回滚；
3. **“卡住了我不知道怎么办。”** → 报错翻译 + 明确的下一步建议。

---

## 3. 产品原则

1. **人定方向，AI 动手**：任何开工前都需要人确认“要做什么”；AI 不擅自扩大范围。
2. **看得懂**：所有输出都提供“大白话版本”，技术细节默认折叠、可展开。
3. **管得住**：随时可暂停；施工中的每一步都可见。
4. **退得回**：任何一次任务都能一键撤销，回到开工前的状态。
5. **不假装**：真实探测本机工具和模型；超时、失败如实告知，不用占位内容掩盖。
6. **不越界**：只使用各工具官方支持的调用方式；不做违反服务条款的自动化。

## 4. 竞争格局（诚实版）

| 类别 | 代表 | 对入门者的问题 | 我们的差异 |
| :--- | :--- | :--- | :--- |
| 官方编码 Agent（CLI / 桌面） | Claude Code、Codex、Cursor Agent、Antigravity | 能力强，但默认用户懂终端、diff、Git | 我们是它们之上的“入门者外壳”，不重复造执行能力 |
| 开源多 Agent 编排 GUI | 多个同类项目 | 面向专业开发者，概念多、配置重 | 只保留一个闭环，概念面向非工程师 |
| 全托管云端生成平台 | 各类“一句话建站/建应用”平台 | 项目困在平台里，复杂后难以继续 | 本地项目、代码归用户所有、可随时转给专业工具继续 |
| 个人工作流工具 | gstack 等 | 命令行 + 斜杠命令 | 吸收其思想（需求剪枝、工程审查、目录约束），以图形化方式呈现 |

**风险提示**：官方产品持续补齐 GUI、任务看板与审批流。因此本项目的护城河**不能是“有图形界面”**，而应是：
1. 面向入门者的**澄清式对话**与**大白话验收**体验；
2. **默认安全**（隔离 + 回滚）的工作方式；
3. **厂商中立**：用户用哪家的工具都能接入。

## 5. MVP 核心闭环（v0.3 ～ v0.5 唯一目标）

```
 ① 说想法 ──► ② AI 澄清提问 ──► ③ 生成一页计划 ──► ④ 人批准开工
                                                        │
 ⑦ 合并 / 回滚 ◄── ⑥ 大白话验收 ◄── ⑤ 隔离分支中施工 ◄──┘
```

### 5.1 ① 说想法
- 用户用自然语言描述想做的事，可附截图或参考链接。
- 界面提供“好想法的写法”示例，降低表达门槛。

### 5.2 ② 澄清提问（吸收 gstack `/office-hours` 思想）
- AI 不直接开写，而是先问 3～5 个关键问题：给谁用、最重要的一件事是什么、什么可以先不做。
- 问题以**选择题优先、可补充文字**的形式呈现，减少用户打字负担。
- 目标：把想法收窄为“这一轮能完成的最小一步”。

### 5.3 ③ 一页计划（Plan Card）
- 内容：这一步要做什么、不做什么、会动到哪些文件（大致范围）、怎么判断做成了（验收标准，用户语言描述）、预计耗时与风险。
- **可选“第二意见”**：一键让另一个模型审阅这份计划，界面并排列出“它认为的问题”与“建议修改”，由用户决定是否采纳。（双模型研讨在 v1.3 中降级为可选功能，见第 8 节验证计划。）

### 5.4 ④ 人批准开工（里程碑 Checkpoint）
- 未经用户点击【批准开工】，任何代码都不会被修改。
- 用户可以修改计划后再批准。

### 5.5 ⑤ 隔离施工
- 每个任务自动在**独立 Git 分支或 worktree** 中进行，主线代码不受影响。
- 用户项目若还不是 Git 仓库，首次使用时由向导以大白话说明并代为初始化（需用户确认）。
- 执行体：MVP 只接**一个**用户本机已安装并登录的官方 CLI（优先 Claude Code，适配器设计保证后续可接入 Codex、Cursor、Antigravity）。
- **权限策略**：
  - 默认**不使用** `--dangerously-skip-permissions` 一类参数；
  - 执行体发起的权限请求转化为界面上的**审批卡片**，附大白话解释（“它想运行 `npm install`，作用是下载项目需要的依赖，通常是安全的”）；
  - 提供“本任务内对低风险操作自动批准”的选项，高风险操作（删除文件、访问项目外路径、联网上传等）始终需人工确认。
- **🔴 暂停**：随时可暂停或终止当前任务（真实向子进程发送信号），暂停后可补充说明再继续。
- 施工过程以**进度时间线**呈现（“正在阅读项目结构 → 正在修改首页 → 正在运行测试”），原始日志默认折叠。

### 5.6 ⑥ 大白话验收
- **改动摘要**：用非技术语言说明改了什么、为什么改。
- **可视化差异**：按文件列出改动，默认展示摘要，可展开查看代码 diff。
- **运行预览**：若是网页类项目，提供一键启动本地预览。
- **报错翻译**：构建或测试失败时，给出“发生了什么 / 可能原因 / 建议下一步”，并可一键让 AI 尝试修复（修复同样在隔离分支内进行）。
- 对照第 ③ 步的验收标准，逐条标注“已满足 / 未满足 / 需要你看一下”。

### 5.7 ⑦ 合并或回滚
- 【满意，保存】：合并到主线，并自动生成一个用户可读的“版本记录”。
- 【不满意，撤销】：丢弃该分支，项目回到开工前状态。
- **历史时间线**：用户可浏览过去每一次任务，并回退到任一保存点。

## 6. 首次使用体验（Onboarding）

入门者流失最多的地方是“装好之前”，因此单列为 MVP 必做项：

1. **环境体检**：自动检测 Git、Node 等基础依赖以及已安装的 AI CLI 与登录状态，用红/黄/绿灯展示。
2. **引导安装**：对缺失项给出逐步图文指引（官方安装方式），不替用户执行需要管理员权限或涉及凭据的操作。
3. **真实模型探测**：读取本机执行体实际可用的模型，不硬编码、不虚构。
4. **示例项目**：提供一个练手模板项目，让用户在 10 分钟内完成第一次“想法 → 合并”的完整闭环。

## 7. 技术实现准则

1. **厂商中立的执行体适配层**：统一接口（启动任务、流式输出、权限请求、暂停/终止、结果收集），每个 CLI 一个适配器。
2. **只走官方支持的调用方式**：
   - 使用各 CLI 公开的非交互/流式输出模式；
   - **不嵌入并程序化驱动** claude.ai、chatgpt.com 等消费级网页；
   - BYOS（复用个人订阅）依赖各厂商当前政策，需在发布前及每次大版本前**核查各家服务条款**，并在 README 中如实说明；若政策变化，提供 API Key 模式作为备选。
3. **真隔离优先于约定**：
   - 任务工作目录限定为项目内的 worktree；
   - v0.x 以 Git 隔离 + 权限审批为主；v1.0 前评估操作系统级沙箱（如 macOS sandbox 配置、容器）以真正限制项目外访问。
4. **超时与失败如实处理**：合理超时（按任务类型可配置），失败给出真实原因，禁止用伪造结果掩盖。
5. **工程健康**：`npm run build`、`tsc --noEmit` 持续全绿；核心闭环需有端到端测试。
6. **隐私**：项目代码与对话仅在本机及用户选择的 AI 服务之间流转，不经过本项目的任何服务器。

## 8. 待验证假设与验证方式

| 假设 | 验证方式 | 通过标准（建议） |
| :--- | :--- | :--- |
| H1：入门者能独立完成首次闭环 | 找 5～8 位符合画像的用户，录屏观察首次使用 | ≥ 70% 在 30 分钟内无外部帮助完成第一次合并 |
| H2：澄清提问能显著减少返工 | 同一批需求对比“直接开写”与“先澄清” | 返工轮次明显下降、用户主观满意度更高 |
| H3：“第二意见”有实际价值 | 10 个真实需求，对比单模型计划与双模型互审计划 | 互审后发现的实质性问题占比可观，且用户愿意为额外耗时买单；否则维持为可选功能 |
| H4：回滚能力降低用户恐惧 | 访谈 + 使用数据 | 用户愿意尝试更大胆的修改，任务尝试次数提升 |
| H5：BYOS 在合规前提下可持续 | 逐家核查服务条款 | 确认符合条款；不符合则切换为 API Key 或官方集成方式 |

## 9. 路线图

| 阶段 | 目标 | 状态 |
| :--- | :--- | :--- |
| **v0.1** | Electron + React 桌面底座、三栏布局原型 | 已完成 |
| **v0.2** | 接入本地 CLI、真实模型探测、超时与日志修复、构建全绿 | 已完成 |
| **v0.3** | **单执行体闭环**：澄清提问 → 计划卡 → 批准 → worktree 隔离施工 → diff 与摘要 → 合并/回滚；真实暂停/终止 | 当前重点 |
| **v0.4** | **入门者体验**：环境体检向导、权限审批卡片的大白话解释、报错翻译、示例项目；完成 H1 用户测试 | 规划中 |

## 10. 成功指标（开源项目）

- **激活**：新用户完成首次“想法 → 合并”闭环的比例；
- **留存**：一周后仍在使用的用户比例；
- **信任**：每个任务中“撤销”的占比，以及撤销后是否继续尝试；
- **社区**：Issue 中来自非专业开发者的反馈占比（检验是否真正触达目标人群）。
