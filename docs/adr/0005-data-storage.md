# ADR 0005：数据存储——第一版用文件，不用数据库；主进程持久化服务是唯一写入者

- 状态：**已批准**（2026-11-08，维护者；9 个验收场景已按评审原文核对）。存储层实现任务必须把第 7 节的 9 个场景写成测试并通过，才算实现完成（测试骨架见 tests/adr-0005-scenarios.test.ts，目前是待实现项，不得删除）。
- 日期：2026-11-08（修订自 BASE-ADR-draft 的 0005 草稿，吸收评审意见与维护者决定）
- 相关：ADR 0006（分层与边界）、ADR 0007（测试分层）、ADR 0008（依赖与供应链，草稿）；依据 M3-BASE-1 现状盘点（HEAD 9044f31）。

## 1. 背景
- 现状全部是 JSON 文件：任务记录 `.studio/tasks/<id>.json`，思考线程 `.studio/threads/`，应用级的最近项目、外发告知、偏好在 userData。
- 写入多为“临时文件 + rename”，但有缺陷：任务记录临时文件名固定；task-prefs.json 直接覆盖写；任务记录无版本字段，解析失败被当作“不存在”；没有跨进程锁；交接清单与任务记录同目录。
- 下一步要做并行施工（同项目多任务、多项目同时运行），写入者变多，必须先把存储与并发规则定下来。

## 2. 决定
1. **第一版用文件存储，不用数据库。** 候选 SQLite（better-sqlite3 是原生模块，需随 Electron 重新编译并放行安装脚本；node:sqlite 的稳定性未确认）暂不采用。
2. **MCP 与持久化无关。** MCP 在本项目里只是 Agent 工具配置：由应用保存，并传给 Codex；它不是存储方案，也不参与任务状态的保存。
3. **唯一写入者**：主进程里的持久化服务（`PersistenceService`）是项目内 `.studio/` 数据与 userData 数据的唯一写入者。渲染进程、执行体适配器（Agent）、core 里的其他模块都不得直接写这些文件，只能通过 Repository 接口（第 5 节）提交变更。
4. **变更协议（乐观并发，CAS）**：每一次状态变更命令都必须带 `runId`、`attemptId` 和 `expectedRevision`。持久化服务在持锁的临界区内比对当前 revision：相等才写入并把 revision 加一；不相等返回 `Conflict{expected, actual}`，**报告给调用方和日志，绝不静默覆盖，也不自动合并重试**（调用方读取最新状态后重新提出）。
5. **`schema_version` 与 `revision` 分开定义**：
   - `schema_version`：记录的**格式**版本（整数），由应用代码决定；读取时低于当前版本则迁移，**高于当前版本则拒绝读取并提示升级应用**，不得当作“不存在”，也不得覆盖。
   - `revision`：该记录每次**成功提交**加一的并发计数，与格式无关；迁移写回算一次提交（revision 加一，schema_version 更新）。
   - `runId`：一次任务运行（每次开工或重新开工生成）的编号；`attemptId`：同一 run 内一次动作尝试（保存、撤销、重试清理等）的编号，用于幂等与日志关联。
6. **事件日志**：每个项目维护只追加的 JSONL 事件日志（`.studio/events.jsonl`）。每行含 `seq`、时间、`runId`、`attemptId`、事件类型、对象、提交后的 `revision`、`schema_version`、载荷。**日志是权威事实来源，汇总数据（任务记录等）是可重建的投影。** 提交顺序：持锁 → CAS 校验 → 追加日志并落盘 → 原子写汇总。
7. **启动对账**：应用启动时先对账——比对汇总的 revision 与日志；日志领先则从日志补写或重建汇总；汇总缺失或损坏则整体重建；日志末行不完整则忽略并报告。**带过期 `runId` 的回传（执行体迟到的事件、旧运行的结果）一律拒绝**，并记入日志。
8. **并行任务**：并行任务各用独立的 Git worktree（现有机制）；同一项目同一时刻只允许一个保存/撤销在进行（项目级保存锁）；后保存的任务若与已前进的主线合并冲突，沿用现有“冲突”流程，**必须提示用户**，不自动处理。
9. **依赖**：`write-file-atomic`（原子写）、`proper-lockfile`（跨进程文件锁，作为单实例锁之外的第二道保险）、`zod`（记录校验）。**引入前按 ADR-0008 检查直接与传递依赖的许可证、安装脚本、原生模块和安全风险**；精确版本、发布满 14 天；任一项不通过则该依赖不引入，改为自写等价实现并另行评审。**检查结果已记录在 ADR-0008 第 4 节：三者均通过**（有一条版本兼容提示，见该节），实际引入由存储层实现任务执行。
10. **单实例**：应用启动时取得单实例锁（`requestSingleInstanceLock`），第二个实例只唤起已有窗口。
11. **目录分开**：任务记录、交接清单、导入报告分目录存放，`list` 不会再把别的文件当成任务。
12. **数据目录限制**：权威数据目录（项目内 `.studio/` 与 userData）**仅支持本地 APFS 磁盘**。启动时检测所在卷；不是本地 APFS（网络盘、外置 exFAT/NTFS、云同步目录等）则拒绝启用写入并提示用户。检测方法在实现任务中确认（本文未确认具体实现）。

### 2.1 状态机、幂等与失败规则（第 7 节场景③④⑦⑧⑨ 依赖这些规则）
- **取消与完成的竞争**：由 CAS 串行化，先提交者胜；后到者收到 `Conflict`，重新读取后按状态机判定。状态机以 `src/core/task/state.ts` 为准：已保存（saved）的任务不能再放弃，只能撤销；已放弃（discarded）的任务不能再保存；终态不接受其他迁移，非法迁移被拒绝并记日志。
- **幂等**：同一 `attemptId` 的重复提交（例如完成事件重复回传）只生效一次——后到的返回首次的结果，不重复提交，也不重复触发副作用（合并、清理、通知等）。去重依据是日志里该 `attemptId` 的完成记录。
- **写入失败**：写临时文件并 fsync 成功之后才 rename；磁盘写满、权限不足等任何一步失败，原文件保持完整，临时文件被清理，失败**显式报告**（不吞错、不静默重试）；日志追加失败则整次提交失败，汇总不改。
- **两个应用进程**：单实例锁之外，用数据目录锁（proper-lockfile）保证同一时刻只有一个独立写入者；拿不到锁的进程不写入，报告并退出或只读。
- **同一源码文件**：每个任务一个独立 worktree，同一 worktree 同一时刻只有一个持有当前 runId 的执行体；不同任务改同一文件，在合并时由 Git 冲突检测发现并提示用户，不存在无提示的最后写入覆盖。
- **并行更新**：同一项目的并行提交经项目级锁串行化；项目汇总是日志的投影，所有已确认（返回成功）的提交在重启后都必须可恢复。

## 3. 理由
- 每个任务一个文件，本身是天然分区；数据量小（每个项目几十到几百个任务）；文件可读、可手工排查，符合“证据可查”。
- 单一写入者 + CAS + 只追加日志，把“多个写入者竞争”变成“一个写入者排队 + 冲突可见”；日志使任何汇总损坏都可恢复。
- 限定本地 APFS，是因为原子 rename、文件锁和 fsync 的语义只在这类本地文件系统上才有保证。

## 4. 后果
- 跨任务查询（“所有已保存且可撤销的任务”“历史搜索”）需要遍历文件或读日志；当前规模可接受。
- 所有现有写文件处（任务存储、偏好、最近项目、外发告知、线程、交接、诊断日志、`.git/info/exclude`）都要迁到持久化服务之后，由后续任务逐项处理。
- **已知风险（需在实现时处理）**：完全信任模式下执行体能写任何文件，可能改动 `.studio/`。应对：读取时用 zod 校验并对账；校验失败标“需要人工查看”，不自动修复。标准模式下执行体只能写任务副本，不能写主项目的 `.studio/`。

## 5. Repository 接口
存储层定义成 Repository 接口（如 `TaskRepository`、`ThreadRepository`、`SettingsRepository`）：`get`、`list`、`commit(command)`（带 runId、attemptId、expectedRevision）、`replay`/`rebuild`。实现为文件版（`File*Repository`，由持久化服务驱动），测试用内存版。**用依赖边界检查禁止 UI 和 Agent 绕过它**（规则见 ADR 0006）。

## 6. 何时重新考虑
单项目任务数上千且列表变慢；需要全文搜索历史；需要跨项目统计；或第 7 节场景在实现中反复暴露文件存储无法满足的问题。届时优先评估 node:sqlite。

## 7. 验收场景（评审原文，写成测试；存储层实现完成的条件）
测试骨架：tests/adr-0005-scenarios.test.ts（目前是 `it.todo`，保留，不得删除）。全部在临时目录里运行，沙箱可跑。

1. **两个 Agent 同时修改同一任务**：不发生静默覆盖，冲突可识别、可处理。
2. **10 个任务并行更新同一项目**：所有已确认提交的状态最终可恢复，项目汇总准确。
3. **任务取消与完成几乎同时发生**：最终状态符合明确的状态机规则。
4. **任务完成事件重复回传**：不重复提交，也不重复触发副作用。
5. **App 退出后重开，旧 Agent 回传结果**：过期运行身份不能覆盖新状态。
6. **保存时进程被强制终止**：可恢复为旧版本或新版本，不接受无法解析的半成品作为权威数据。
7. **磁盘写满、权限不足**：原有效数据保持完整，失败显式报告。
8. **两个应用进程尝试操作同一数据目录**：不允许两个独立写入者同时提交。
9. **两个 Agent 修改同一源码文件**：隔离或冲突检测生效，不出现无提示的最后写入覆盖。

对应的规则见第 2、2.1 节（CAS、runId、状态机、幂等、写入失败、数据目录锁、worktree 隔离）。

**附加检查（不计入上面 9 条，由存储层实现任务一并测试）**：汇总丢失或损坏时由日志重建、逐字段一致；日志末行被截断时忽略并报告；读到更高的 `schema_version` 时拒绝读取而不是当作不存在；数据目录不在本地 APFS 时拒绝启用写入并提示（检测接口可注入）。


## 8. 实现状态（2026-11-09）
已实现（src/core/persistence/，测试见 tests/adr-0005-scenarios.test.ts、tests/persistence.test.ts）：
- Repository 接口与文件版实现（`RecordStore`）：每次提交带 runId、attemptId、expectedRevision，做 CAS；冲突、过期运行、重复提交都显式返回并写入日志；`schema_version` 与 `revision` 分开；zod 校验记录的关键字段（其余字段原样保留）。
- 只追加的 JSONL 事件日志（`.studio/events.jsonl`，补丁式记录，汇总可由它重建）与启动对账；运行编号换新（fence）后旧运行的回传一律拒绝；施工中被中断的任务在重启后按失败收尾。
- 唯一写入者：数据目录租约（proper-lockfile）+ 进程内串行 + 主进程单实例锁；写文件用 write-file-atomic；数据目录必须在本地 APFS（`df` + `mount` 判断，探测接口可注入）。
- 已改走记录库：任务记录、最近项目、外发告知确认、任务偏好、诊断记录（日志事件）、`.git/info/exclude` 的追加；旧文件第一次打开时迁移（旧文件改名为 `.migrated` 保留）。
- 依赖边界检查（tests/security.test.ts “ADR 0006：持久化依赖边界”）：src 里只有 persistence/ 能直接写文件（豁免只有模拟执行体写任务副本），记录库只能被指定模块引用，UI 与 Agent 不得引用。

与本文原定内容的差别（如实记录）：
1. **思考线程（`.studio/threads/`）、交接清单与导入报告（`.studio/tasks/`）、`consent.json`、方案文档**没有改成记录库提交（没有 CAS 与事件日志），它们的写入统一经 persistence/files 里的原子写/不覆盖写原语（write-file-atomic）；它们是单写入者的命令行流程产物或一次性写入。后续任务可把线程记录也迁入记录库。任务记录搬到了 `.studio/records/tasks/`，交接清单仍在 `.studio/tasks/`，所以 `list` 不会再把清单当成任务。
2. 项目级保存互斥目前是“每个项目一个控制器、一个编排器”里的任务级互斥（同一任务的保存/放弃/撤销互斥）；跨任务的项目级保存锁没有单独实现——并行任务各自保存时由 Git 合并冲突检测兜底（场景 9 已验证）。
3. 事件日志没有轮转或压缩。
4. 引入时把项目 `engines` 收紧为 `>=22.22.2 <23`（write-file-atomic 的要求）；.nvmrc 仍是 `22`（解析为最新 22.x，满足要求）。Electron 45 内置 Node 的版本未确认。
